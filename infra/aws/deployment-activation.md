# Protected EC2 deployment: prepared, inactive

The checked-in identity and deployment manifests are disabled. No environment, AWS role/document, runtime secret, DNS/certificate, image publication or real deployment has been activated or executed by this change. GitHub runs use disposable local containers and synthetic configuration. The PR remains Draft while the mandatory external activation from #35 is absent.

The owner must approve provisioning/reconciliation, protected existing environments, the tested source and migrations, and the actual deployment separately. Set `controlled_deployment` only after reviewing its TLS/CA paths, selected retained EC2/EBS, dedicated deployment identity and private repositories. Its account-owned SSM document embeds the reviewed host runner, complete Compose runtime and public contract; Terraform itself never invokes it. `github_deployment_identity.document_arn` must name that exact document. Existing custom documents require explicit owner review/import; do not overwrite unreviewed documents.

After separately authorized provisioning, export the actual `controlled_deployment` output. Populate `.github/aws-deployment.json` from those public values: environment/role matching the approved identity, exact instance, numeric document version, **AWS-produced Sha256 document hash**, public contract and its fingerprint. Do not substitute `$DEFAULT`, `$LATEST`, invented IDs or an inferred region/domain. Keep `enabled:false` and `ENABLE_EC2_DEPLOY` unset until the owner approves activation. Reconcile any runner/Compose or Terraform contract change before updating the approved export. The deployment helper rejects mismatched source hashes and SendCommand binds the exact document version/hash; it does not apply Terraform or broaden the role.

The selected host must already have its retained upload volume mounted by the reviewed #25 storage helper, the private `/srv/laravel/runtime/application.env` prepared by #27 with the stable APP_KEY, trusted RDS CA under the selected public path and matching `DB_SSLROOTCERT=/run/database-ca/rds.pem`, and approved TLS certificate/challenge directories from #29. TLS CA can be empty for the system trust store or an explicit trusted public CA file. Never place private keys or runtime env in release records, repository, artifacts or logs. All four PHP processes use that same env file (`format:raw`), RDS CA and EBS bind. Nginx alone exposes 80/443, and readiness validates HTTPS `/ready` with native TLS trust rather than Nginx's configuration-only `/up`.

Manual `deploy.yml` requires `deploy:true`, activated manifests, `ENABLE_EC2_DEPLOY=true`, `main`, an already protected environment with reviewers and an approved retained producer from #34. The read-only preflight validates the environment before scheduling it; the approved job checks immutable IDs again before obtaining a signed token. The same verified JWT is passed to the separate deployment role. No PR/push receives credentials, no image is rebuilt or republished, and complete OCI archives are never uploaded by this deployment workflow.

Each request binds full source SHA, SemVer, real image manifest digests, original manifest/asset fingerprints and the completed current release as N-1. Initial release must be explicit. The host serializes with `flock`; GitHub serializes per environment without cancelling an active deployment. It verifies the exact retained EBS device, immutable image provenance and available predecessor, then runs #20 migration once before stopping old worker/scheduler. Migration failure preserves the completed receipt and running release. Expand/contract compatibility with both N and N-1 must be reviewed by the approving owner; `schema_policy:expand-contract` records that policy, not an automated proof of migration reversibility.

After migration succeeds, private `runtime/releases/state.json` records the pending phase. Promotion stops processes with 90s grace, starts web, requires readiness, starts one worker/scheduler and checks readiness again before atomically recording completed current/previous. Files are private/owned, source/assets are shared, and a completed retry rechecks health without rerunning migration or replacing processes. Receipts contain timestamps and public identity/configuration only. A failed or interrupted candidate retains the last completed receipt plus pending identity/phase, stops candidate services when possible and blocks further promotion until the separately approved #37 recovery operation. A completed pointer with pending state is not evidence of a currently healthy application. No automatic database reverse migration, `down -v`, volume deletion or compensation occurs.

SSM output is restricted to the exact public receipt. AWS/tool/SQL/credential diagnostics are withheld; the regional GetCommandInvocation permission's documented limitation from #35 remains. An unknown acknowledgment or observation timeout requires inspecting the known command privately before retrying; the workflow never blindly retries SendCommand or cancels a host command. Monitoring metadata from #30 is owner-configured and is not refreshed here or presented as proof of the running image. This scope does not claim full N→N+1→N recovery; #38 exercises that cycle separately.
