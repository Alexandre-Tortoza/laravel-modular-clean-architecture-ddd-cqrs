# Recovery planning and disposable rehearsal

Recovery creates a **new database, upload volume and host**, preserving the source. No helper here executes an AWS API, attaches a disk, changes DNS, formats a restored filesystem, overwrites an existing target or deletes production data. A real restore/cutover needs explicit owner approval of account, region, selected backups, network, capacity, KMS/IAM and application compatibility.

`python3 infra/aws/scripts/restore_plan.py --config APPROVED_PUBLIC_METADATA.json` produces an offline JSON plan. There is no execute option. The input schema is illustrated by the synthetic `fixture()` in `infra/aws/tests/test_restore_plan.py`: source DB/volume/host IDs, administrator/application secret ARNs, original storage KMS key and APP_KEY fingerprint; distinct target DB/volume/host names and application secret; private subnet-group membership/SG bindings; PostgreSQL TLS parameter group/CA; one selected database restore point and upload snapshot. Do not put secret values or actual APP_KEY/passwords in that file, Terraform, commands, logs or evidence. The plan validates supplied metadata; it does **not** prove AWS resources/permissions, snapshot ownership, network reachability or KMS/CA validity.

## Owner-approved operational sequence

1. Record source identity, release digests/receipts, backup times and logical/upload checksums. Select a DB snapshot bound to that source, or an explicit UTC PITR timestamp inside its recorded earliest/latest restorable window. Select the upload EBS snapshot and a consistent recovery point; independent DB/EBS snapshots do not guarantee application consistency. Pause writes or reconcile differences under a reviewed procedure. Never infer a recovery time from the current clock or silently use latest.
2. Review the new target labels/identifier. Verify the selected DB subnet group contains the declared private subnets in at least two AZs and the DB SG permits PostgreSQL only from the new recovery host SG. Require no public DB/host exposure, the approved PostgreSQL 16 TLS parameter group/CA and `verify-full`. Explicitly arrange private-host access to SSM, ECR and Secrets Manager; no paid network resources are inferred or activated by the plan.
3. Restore to the **new DB instance identifier** using the reviewed [snapshot restore](https://docs.aws.amazon.com/AmazonRDS/latest/APIReference/API_RestoreDBInstanceFromDBSnapshot.html) or [PITR](https://docs.aws.amazon.com/AmazonRDS/latest/APIReference/API_RestoreDBInstanceToPointInTime.html) operation. Supply the intended subnet/security/parameter groups and public-access setting explicitly; do not accept inherited/default groups. Preserve encryption with the approved source storage key. Verify the new endpoint, actual groups, CA and encryption before connecting.
4. Request a new managed administrator secret for the restored DB, protected by the selected KMS key, and verify its ARN differs from the source administrator secret. Reconcile a separate non-admin application role/password for the new target. Do not copy the original administrator secret or an old DB password into the application runtime file.
5. Create a **new encrypted EBS volume** from the selected upload snapshot in the new host's AZ. Verify its actual source snapshot, filesystem and immutable device/volume binding before mounting; leave initialization/formatting disabled. Retain owner 33 and private directory/file permissions. Never attach/format the source volume as a restore target or mount both copies ambiguously by a shared filesystem UUID.
6. Recover only the original APP_KEY field through its approved application-secret authority into a separate target application secret; verify its private fingerprint. Set new DB connection credentials separately. SQL/EBS backups alone do not recover Secrets Manager versions/APP_KEY, administrator credentials, TLS private keys or external services. Start with the corresponding retained image digests/configuration and schema compatibility; do not run destructive migrations or reverse external effects.
7. Compare rows, migrations/release receipts, queued-job/session structures, upload inventories and decryption; then perform actual login/session, readiness and worker/scheduler smoke tests. Measure achieved recovery point/duration against the owner's RPO/RTO. Keep timestamps and a sanitized result. Approve traffic cutover separately only after validation; keep the source and previous receipts for manual recovery. Removal of any target/source resource is a separate approved operation.

The existing opt-in RDS automated/final-backup retention and encrypted upload DLM snapshot policy remain the backup controls. Single EC2/Single-AZ RDS are failure domains; periodic snapshots are not availability or verified restores. Snapshot schedules/retention do not prove RPO, RTO, consistency, cross-account recovery or retention of secret/KMS access.

## What the CI proves

`backup-restore-contract.yml` runs only on a disposable GitHub-hosted Linux runner. Its script accepts no external target arguments, rejects remote Docker contexts and requires an explicit fixture acknowledgement. Two PostgreSQL 16.15 containers use `network:none`, no published ports and separate tmpfs clusters/passwords. Two uniquely named, ownership-labelled upload volumes are created; cleanup removes only those resources.

The fixture performs a real `pg_dump` custom backup and [single-transaction `pg_restore`](https://www.postgresql.org/docs/16/app-pgrestore.html) into an empty new DB. It compares representative user/session/job/migration/release-receipt rows, column definitions, indexes, constraints and sequences; rejects a corrupt archive and reuse of an occupied target; checks source logical/upload hashes remain unchanged. A new UID-33 upload volume receives a tar restore with private modes intact. Independently retained synthetic APP_KEY material decrypts the fixture upload; a different key does not reproduce its contents.

This is a **logical PostgreSQL and filesystem/key rehearsal**, with representative SQL structures and OpenSSL fixture encryption. It is not an AWS RDS snapshot/PITR or EBS restore, a Laravel Crypt/HTTP login/cookie test, a live IAM/KMS/SSM test, a production-sized timing measurement or proof of production RPO/RTO. Test databases, dumps, keys, private payloads and archives are removed on exit; only the sanitized JSON hashes/status/timestamps are uploaded. Real AWS snapshot/PITR and end-to-end application recovery remain unproven until separately authorized and measured.
