# Architecture and module contract

This starter kit has four modules: Identity, Profile, Security, and Teams. Each module keeps used code under `app/Modules/<Module>/Domain`, `Application`, `Infrastructure`, `Presentation`, and `routes`. A module need not create every folder. Global Laravel bootstrap, Inertia sharing, Fortify response adapters, and the technical database migrations remain global composition code.

## Ownership and dependencies

| Data or operation          | Reader                                                                                                                   | Writer                                                                                 | Rule                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `users` identity and email | Identity; Teams through `UserDirectory`; Profile validation through `UserDirectory`; Security through `SecurityAccounts` | Identity through `ProfileAccounts`, `AccountCredentials`, or the Fortify reset adapter | No external module imports the Eloquent User model                              |
| `current_team_id`          | Identity `UserDirectory`; Teams through it                                                                               | Identity `TeamSelectionAccounts`, called only from Teams write flows                   | Teams verifies membership and permission while its transaction is active        |
| `teams`, `team_members`    | Teams queries and adapters                                                                                               | Teams handlers through internal ports                                                  | A team row and affected users are locked before concurrent membership decisions |
| `team_invitations`         | Teams queries and adapters                                                                                               | Teams invitation handlers through an internal port                                     | Expiration and recipient rules run inside the write transaction                 |

The dependency graph is Profile → Identity and Teams, Teams → Identity, and Security → Identity. Identity has no dependency on those modules. Profile may use only Teams' purpose-built account-deletion API; it does not import Teams models, handlers, or internal contracts. Global bootstrap may compose providers and framework adapters. There is no reverse dependency from Identity to Teams or duplicated User model. The Teams tables remain on the same database connection as `users`. Profile and Security are functional subdivisions of identity/access, not independently modeled bounded contexts; Teams represents the collaboration model. Code modules do not imply independently deployable services or databases.

`Application/Api` is the exported surface. `Identity/Application/Api/UserDirectory` and `SecurityAccounts` return read-only scalars, arrays, or immutable `UserRecord`. `ProfileAccounts::updateOwnProfile(actorId, name, email)` accepts the desired change and atomically locks, compares, and saves only the authenticated executor account. Identity's pure `EmailVerificationPolicy` invalidates verification whenever that email changes; callers cannot choose to retain it. `AccountCredentials` accepts an authenticated executor ID and a new password. These APIs do not accept a separate target ID. The HTTP layer obtains that ID from the authenticated request; direct callers must establish a trusted actor context. Password confirmation and input validation occur at the request boundary. Fortify's token-based reset flow is its own framework adapter.

`TeamSelectionAccounts` is a separate, Teams-only Identity write integration. It locks users in ascending ID order, requires an active transaction on the User connection, identifies users selecting a team, and updates `current_team_id`. Teams create and invitation-accept handlers call it explicitly in their transaction. Leaving or deleting the selected last team stores `null`; operating on another team preserves the selection. It is not a public user-facing authorization mechanism. The architecture suite rejects use from Profile, Security, or another module. `TeamContext` is the exported read-only Teams context for Inertia/Fortify and other trusted composition code. A team slug resolved by middleware is request context only: GET and HEAD requests never persist it. The explicit team-switch command is the only HTTP flow that changes `current_team_id`. `TeamQueries` is an internal query port; `editFor(actorId, teamId)` rejects a caller without team membership even when invoked outside HTTP middleware. Read operations do not modify selection or send notifications.

`AccountTeamLifecycle::deleteResourcesForAccount(accountId)` is a Profile-only Teams API requiring an active transaction on the shared connection. `DeleteProfile(userId)` does not carry an email snapshot. `DeleteProfileHandler` opens the Profile transaction, invokes that API, and only then asks Identity to delete the account. Teams locks the discovered active teams in ascending ID order, obtains the authoritative email from the locked Identity user, and re-reads memberships. A membership outside the protected set rejects the complete operation; no additional team locks are acquired after the user lock. The caller may retry with a fresh snapshot. Ownership rejection also applies when the account owns a shared team or a personal team with other members. A successful deletion removes memberships, revokes all invitations sent by the account and only pending invitations received at its current email, and closes only its sole-member personal teams. Received accepted invitations and invitations to an old email are preserved unless owned by a team being closed. It never transfers ownership or deletes a shared team. A rejected HTTP request keeps its authenticated session because logout occurs only after the transaction succeeds. Database cascades are cleanup protection, not the Team lifecycle policy.

External modules use `Application/Api` interfaces and the immutable data types in their signatures. Internal `Application/Contracts` ports, handlers, Eloquent models, builders, relations, and framework collections are not exported. Infrastructure may use Laravel and Eloquent to implement a module's own ports and may call another module's explicit API. Presentation translates requests, responses, redirects, and flashes. Domain contains pure PHP policies and enums and has no framework dependency.

## Write flow: inviting a member

`POST settings/teams/{team}/invitations` enters `CreateTeamInvitationRequest` for format validation and `TeamInvitationController` for HTTP authorization and response handling. The controller constructs immutable `CreateTeamInvitation` and invokes its dedicated `CreateTeamInvitationHandler` directly. The handler opens the Teams transaction through `RunsTeamTransactions` and asks `ManagesTeamInvitations` for a snapshot protected by a team row lock, pending invitation locks, and ascending user locks through Identity `TeamSelectionAccounts`. `InvitationPolicy` then checks the inviter role, recipient membership, assignable role, and existing pending invitation, and defines the expiration three days after the supplied clock instant. The adapter persists that instant and the handler requests a notification after the write. `TeamInvitationSender` uses Laravel's queued `afterCommit()`, so an outer transaction still controls delivery and rollback discards it. The controller returns the existing redirect and flash response.

A matching read goes through `TeamQueries::editFor` for the team edit page. It verifies membership before projecting members, pending invitations, and effective permissions into plain data; a personal team never advertises deletion. Pending invitation authors are fetched in one batch through Identity's `UserDirectory::findMany()`. The query does not reconstruct an aggregate or write. Tests cover the policy without Laravel boot, handler port orchestration, direct read authorization, HTTP/Inertia responses, persistence, external commit/rollback, and PostgreSQL concurrency.

Accepting or declining an invitation requires the current account email to be verified. HTTP routes use `auth` and `verified`; handlers independently apply the pure policy to `InvitationResponseData`, populated from the locked Identity `UserRecord.emailIsVerified`. A stale authenticated object or command cannot establish mailbox ownership. HTTP middleware redirects an unverified browser to the verification notice and returns 403 for JSON; an expected rejection reached inside a handler retains the existing invitation validation mapping. `currentForUser` projects the team and membership together, excluding soft-deleted teams. Its fallback remains read-only.

`TeamLifecyclePolicy` and `InvitationPolicy` hold rules for owner, role, membership, personal-team deletion/leave, recipient, and expiration decisions. `TeamNamePolicy` is a pure rule shared by create and update handlers: a trimmed name is required and its original input is limited to 255 characters. Presentation retains route/slug-specific validation. A personal team is personal to its owner membership, not every member; personal-team lookup requires ownership. The team row and its membership or invitation rows form the lock-protected consistency scope for Teams decisions. Team deletion discovers actor candidates and personal fallbacks of users selecting the target, locks those teams in ascending ID order, then locks affected users in ascending ID order. Protecting other users' personal fallbacks avoids a PostgreSQL FK lock inversion during opposing deletions. A fallback that appears outside that protected set rejects the deletion rather than acquiring a later team lock. Coordinated PostgreSQL tests observe actual blockers; transaction-start events distinguish retries from additional lock queries. These tested scenarios are not a proof that every lifecycle race is covered. A single use case may also update Identity's current-team pointer in the same local database transaction. That wider transaction is the **transaction boundary of the use case**, not a claim that every affected row is one domain aggregate. No synthetic aggregate hierarchy or Eloquent duplicate was added.

## Database resources and upgrades

Identity owns the User model and its factory under `Infrastructure/Persistence/Eloquent`; the factory creates only a user. `Tests/Support/UserWithPersonalTeam.php` explicitly composes a user and personal team through the Teams create use case for tests. Standard `DatabaseSeeder` creates no demonstration data. Global `DemoDatabaseSeeder` explicitly composes Identity's `DemoUserSeeder` and Teams' `DemoPersonalTeamSeeder` in order and is safe to rerun. Each demo entry point rejects environments other than `local` and `testing` before any write, even with `--force`. Factories keep predictable credentials for tests; they are not production account provisioners. Providers register each module's bindings, routes, migrations, and Teams policy/schedule. `bootstrap/providers.php` composes the providers.

Exclusive passkey and two-factor migrations are loaded from Identity; exclusive Teams migrations remain in Teams. The historical `0001_01_01_000000_create_users_table.php` creates `users`, `password_reset_tokens`, and `sessions` together, so it remains **unchanged and global**. This provisioner location does not grant other modules access to Identity's data. Technical cache, job, and AI migrations also remain global. Existing basenames, timestamps, and schema effects are preserved; no migration is split, duplicated, or replayed to enforce a directory convention. For an existing database, use `php artisan migrate --force` after updating code; do not reset a live database. Verify a fresh install and an upgrade against separate disposable databases.

## Adding a module

Follow the [tested practical workflow](docs/modular-development.md) for native generators, a complete small module, explicit seeding and Wayfinder. The example runs in a separate disposable copy; it does not add a business module to the distributed template.

1. Assign table and behavior ownership, then define any real Domain policy or value type. Avoid an empty layer or a model duplicate.
2. Add one immutable command and dedicated handler per write use case. Put internal persistence and effect ports in `Application/Contracts`; export only integration contracts needed by another module through `Application/Api`.
3. Implement owned storage, migrations, factories, seeders, and bindings in Infrastructure. Keep existing migrations immutable. Put HTTP validation, routes, response mapping, and middleware in Presentation and register them through the module provider.
4. Test the rule without Laravel boot, the handler with relevant doubles, adapters with the database, cross-module access, HTTP/Inertia behavior, and concurrency where locks matter. Run the architecture suite; a newly added module is discovered automatically and forbidden dependencies fail the suite.
5. Register the provider in `bootstrap/providers.php`, regenerate Wayfinder if routes changed, then run `composer test`, `COMPOSER_PROCESS_TIMEOUT=0 composer coverage`, `composer ci:check`, `npm run build`, migrations, seed, route/config caches, and the PostgreSQL concurrency suite against disposable environments.

The architecture inspector parses PHP source to discover modules, dependency edges, Eloquent placement, public signatures, immutable commands, data and API value classes, and framework helper calls. Temporary fixtures prove that a new forbidden module dependency and a mutable public value fail. Module discovery is automatic, but authorized consumers of restricted APIs are explicit policy in the inspector; extending an API's consumers requires updating that policy and its tests deliberately. A future pure `App/Shared/Domain` type is allowed only without a reverse module or framework dependency; no Shared directory is created until real consumers need it. Static checks cannot detect every dynamic container lookup, SQL string, or authorization mistake; behavioral and database tests provide separate evidence. CI runs standard checks and PostgreSQL concurrency. The exact coverage gate runs locally with `COMPOSER_PROCESS_TIMEOUT=0 composer coverage` and on demand in CI through `workflow_dispatch` once the workflow is available on the default branch. `afterCommit()` delays notification dispatch until commit; it does not guarantee durable delivery across database and queue failures.

## Deferred, non-blocking work

This closing change does not redesign interfaces, add buses or synthetic aggregates, or specialize Teams for an ERP. Further fallback eligibility refinement (including a generic fallback list containing another owner's personal team), imported invitation-role validation, extra leave/removal interleavings, and static analysis of the entire test tree remain separate follow-up work. None is described here as an implemented guarantee. The template includes MIT licensing and starter attribution, generic project metadata, minimum-version validation, independent-template smoke tests and prepared release workflows. Publication and external activation are separate opt-in operations; setup and build scripts do not publish releases.
